เมื่อคนในองค์กรสามารถสั่ง AI ให้สร้าง web แอปพลิเคชัน, script, dashboard
หรือ automation ได้ในไม่กี่ชั่วโมง
ซอฟต์แวร์ที่เคยต้องรอทีม IT กำลังถูกสร้างขึ้นโดยคนที่ไม่ใช่นักพัฒนา

หลายอันเริ่มจากงานเล็กๆ เช่น ดึงข้อมูลจาก spreadsheet มาสรุปผล ส่งอีเมลอัตโนมัติ
หรือทำหน้าจอให้ทีมกรอกข้อมูลเอง แต่เมื่อมันเริ่มเชื่อมต่อฐานข้อมูล
ใช้ข้อมูลลูกค้า หรือกลายเป็นส่วนหนึ่งของ workflow สำคัญ
แอปลิเคชันเหล่านั้นก็ไม่ใช่ส่วนเล็กๆที่มองข้ามได้

ปัญหาคือคนสร้างมักไม่ได้อ่าน code ที่ AI สร้าง
และต่อให้เปิดอ่านก็อาจจะตัดสินไม่ได้ว่าปลอดภัยจริงหรือไม่

## เป็น 3rd party software หรือไม่เป็น?

คำตอบคือเป็นทั้งสองอย่าง แต่ไม่ควรเรียกรวมกันว่า 3rd party software แล้วจบ

ตัว AI coding tool, model, plugin, cloud hosting, package
และ API ที่ใช้เป็น third party จริง
องค์กรต้องประเมินเรื่องข้อมูลที่ถูกส่งออกไป เงื่อนไขการใช้งาน
การเก็บข้อมูล ความต่อเนื่องของผู้ให้บริการ
และความเสี่ยงของ dependency เหมือนที่ประเมิน SaaS หรือ vendor ทั่วไป

แต่แอปพลิเคชันที่พนักงานสร้างขึ้นมาเป็นซอฟต์แวร์ขององค์กรเอง เพราะองค์กรเป็นคนกำหนดโจทย์
ถือข้อมูล เลือกนำไปใช้งาน และรับผลเมื่อมันผิดพลาด
ถึงจะไม่มีใครในองค์กรเขียน code ทีละบรรทัดก็ตาม

ดังนั้นนโยบายขององค์กรควรนิยามแอปพลิเคชันลักษณะนี้เป็นอีกประเภทหนึ่ง
เช่น **AI-assisted employee-developed software**
หรือ **AI-generated internal แอปพลิเคชัน** แล้วกำกับทั้งในฐานะ internal software
และ third-party supply chain

ถ้าจัดเป็น third party อย่างเดียว จะมีช่องโหว่ว่า "ไม่มี source code ที่เราดูแล"
แต่ถ้าจัดเป็น internal software อย่างเดียว ก็จะมองข้ามความเสี่ยงจาก model,
package, service และข้อมูลที่ส่งให้ vendor

## ความเสี่ยงไม่ได้ดูที่ชื่อของเจ้าของแอปพลิเคชัน

ต่อให้เป็นแอปพลิเคชันที่ฝ่าย IT หรือพัฒนาซอฟต์แวร์ทำเองโดยเฉพาะ
ก็ไม่ควรตัดสินว่าไม่ใช่ความเสี่ยง
ความเสี่ยงของซอฟต์แวร์ที่สร้างต้องถูกวัดด้วยมาตรฐานเดียวกันว่าใช้ทำอะไร
เข้าถึงอะไร และถ้าพังแล้วกระทบใครบ้าง

- ใช้ส่วนตัว ไม่เก็บข้อมูล ไม่เชื่อมต่อระบบ: อนุญาตได้ภายใต้เครื่องมือ AI ที่องค์กรอนุมัติ
- ใช้ในทีม แต่มีข้อมูลภายใน: ต้องแจ้งทะเบียน source code, owner และเครื่องมือที่ใช้
- เชื่อมต่อระบบองค์กร หรือส่งข้อมูลออกไปภายนอก: ต้องผ่าน security review และใช้ account/service credential ขององค์กร
- แตะข้อมูลส่วนบุคคล ข้อมูลการเงิน สิทธิ์ production หรือใช้ตัดสินใจแทนคน: ต้องผ่าน review แบบเดียวกับ production แอปพลิเคชันปกติ

ไม่ควรมีช่องว่า "เป็นแค่ของที่พนักงานทำเอง" เพราะคำนี้ไม่ได้ลดผลกระทบของความผิดพลาด

## นโยบายขั้นต่ำที่ควรมี

1. **มีทะเบียนของแอปพลิเคชัน**

   ระบุ owner, ผู้ใช้, จุดประสงค์, data classification, AI tool/model, package สำคัญ,
   repository, hosting และสิทธิ์ที่แอปพลิเคชันใช้ อย่างน้อยองค์กรจะรู้ว่ามีอะไรอยู่บ้าง

2. **กำหนด AI tools ที่องค์กรอนุมัติและข้อมูลที่ใช้ได้**

   AI tool ที่องค์กรอนุมัติควรใช้กับ account หรือ service ที่องค์กรจัดการได้
   เช่น ตรวจเงื่อนไขการเก็บข้อมูลได้ กำหนดสิทธิ์ผู้ใช้ได้ ถอนสิทธิ์เมื่อพนักงานออกได้
   และตรวจสอบการใช้งานได้
   โดยกำหนดนโยบายห้ามไม่ให้ส่ง secret, credential, source code
   หรือข้อมูลลูกค้าเข้า account ส่วนตัว หรือ AI service ที่ยังไม่ผ่านการอนุมัติ

   ตัวอย่าง: องค์กรควรห้ามการใช้ ChatGPT account ส่วนตัว
   การสร้างเอกสารที่มีข้อมูลของลูกค้า

3. **ต้องมีคนรับผิดชอบที่อ่านและรับรองผลลัพธ์ได้**

   ไม่จำเป็นต้องให้ผู้ใช้ทุกคนกลายเป็น developer แต่ทุกแอปพลิเคชันต้องมี owner
   และมีผู้ที่มีความสามารถพอจะ review code, architecture
   และการเปลี่ยนแปลงตามระดับความเสี่ยง
   ซึ่งในความเสี่ยงที่ค่อนข้างต่ำ เราอาจสร้าง AI agent มาทำหน้าที่ review ส่วนนี้แทน และแจ้งเตือนลงในระบบหากพบปัจจัยเสี่ยง

4. **ใช้ process เดียวกับ software ปกติเมื่อความเสี่ยงสูงขึ้น**

   เก็บ source code ใน repository ขององค์กร, ใช้ code review, test,
   dependency scanning, secret scanning, access control, logging, backup
   และช่องทาง deploy ที่ตรวจสอบย้อนหลังได้
   การที่มี AI ช่วยสร้าง code ของโปรแกรมไม่ใช่เหตุผลให้ข้าม process ปกติ

5. **ห้ามใช้ credential ของคนสร้างเป็น production credential**

   ใช้ service account ที่มีสิทธิ์เท่าที่จำเป็น หมุน secret ได้
   ถอนสิทธิ์ได้ และรู้ว่าแอปพลิเคชันไหนใช้มันอยู่
   เมื่อพนักงานลาออก งานต้องไม่หายไปพร้อม account ของเขา

6. **กำหนดทางออกตั้งแต่ก่อนอนุญาตให้ใช้**

   ต้องรู้ว่าใคร maintain, ปิดระบบอย่างไร, export data ได้หรือไม่
   และเมื่อ vendor เปลี่ยนราคา เปลี่ยนเงื่อนไข หรือหยุดให้บริการ จะทำอย่างไร

## มีมาตรฐานแล้วหรือยัง?

ยังไม่มีมาตรฐานสากลที่บอกตรงๆ ว่า
"code ที่พนักงานสร้างด้วย AI ต้องถูกนับเป็น third party software"
แต่มาตรฐานเหล่านี้ก็สามารถนำมาใช้ประกอบการสร้างนโยบายได้

- [ISO/IEC 42001:2023](https://www.iso.org/standard/42001) เป็นมาตรฐาน AI management system สำหรับองค์กรที่พัฒนาหรือใช้ AI โดยเน้น นโยบาย, responsibility และการจัดการความเสี่ยง
- [NIST AI RMF](https://www.nist.gov/itl/ai-risk-management-framework) และ [Generative AI Profile](https://nvlpubs.nist.gov/nistpubs/ai/NIST.AI.600-1.pdf) วางกรอบ Govern, Map, Measure, Manage เพื่อให้ประเมินและติดตามความเสี่ยงตาม use case
- [NIST SSDF](https://csrc.nist.gov/pubs/sp/800/218/final) เป็น baseline สำหรับ secure software development และ [SP 800-218A](https://nvlpubs.nist.gov/nistpubs/SpecialPublications/NIST.SP.800-218A.pdf) เพิ่มข้อพิจารณาสำหรับ generative AI และ foundation model
- [OWASP Secure Coding with AI Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Secure_Coding_with_AI_Cheat_Sheet.html) ระบุความเสี่ยงที่เห็นได้ทันที เช่น dependency ที่ AI แต่งขึ้น, dependency เก่าที่มี CVE และ prompt injection ใน development workflow

## จุดที่องค์กรต้องยอมรับ

AI จะทำให้จำนวนคนที่สร้างซอฟต์แวร์ได้เพิ่มขึ้นเร็วกว่าจำนวนคนที่ตรวจซอฟต์แวร์เป็น
ทางเลือกจึงไม่ใช่ห้ามทุกคนสร้าง เพราะสุดท้ายจะกลายเป็น shadow IT ที่มองไม่เห็น

สิ่งที่ควรทำคือทำทางที่ปลอดภัยให้ใช้ง่ายพอ:
มี AI tool ที่อนุมัติ, template, repository,
deployment path, review และคนช่วยดูตามระดับความเสี่ยง
